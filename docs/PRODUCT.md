# SOBER v1 — Product requirements

What SOBER does, from the user's side. `SCOPE.md` says which capabilities exist;
this file says how they behave. Every requirement traces to a SCOPE MUST.

Status: **elicited 2026-08-27, revised 2026-08-28** by the review that produced
ADRs 0006–0018. All nine sections are written. Every requirement traces to a MUST
in `SCOPE.md`; every non-obvious choice behind them is in the decision table below
or in `docs/adr/`.

Requirements are settled. Mechanism is not: `DESIGN.md` still carries OPEN markers,
each tied to the phase that closes it. Requirements marked **M2** or **M3** are v1
requirements that ADR 0015 orders after the loop closes once.

loop; the MUST column carries the traceability.

| D32 | Where work is reviewed, and when a pull request is opened | **A draft pull request per node, opened when a run finishes** (when a remote exists and the setting is on). **Review happens in SOBER**, showing the diff, the CI result, and the scan together. **M2.**                      | The pull request is a mechanism for getting CI, not the review surface. One per node, not per attempt (ADR 0012).                                                                                                                                                         |
| D33 | What accept does                                          | **Configurable: merge locally, or mark the pull request ready and merge it.** Default is whatever the project supports — local merge with no remote, which is M1's case.                                                      | A protected main cannot take a local merge; a repo with no remote cannot take a pull request.                                                                                                                                                                             |
| D34 | What reject does                                          | **Reject with feedback, and run again.** The node returns to `ready`; the next run carries the feedback and, by default, the previous attempt's work. The branch, worktree and draft pull request are the node's and are not multiplied per attempt (ADR 0012).                                                                                                                        |
| D35 | The shape of sync                                         | **One action: pull, merge, then push.** Never automatic, never on dashboard open. A fetch is not a pull and may be automatic. **M2.**                                                                                         | One mental model instead of two. The digest depends on the fetch/pull distinction.                                                                                                                                                                                        |
| D36 | Board conflicts                                           | **Resolved field by field, in the dashboard** (ADR 0013). A field only one side changed is taken automatically; a field both changed is put to the user. The user never sees a conflict marker. **M2.**                       | Whole-record choice discards a co-editor's work. Three versions are in git's index, so field-level costs nothing extra. | D37 | What can be done with a flagged node                      | **Three actions: dismiss with a reason, run again, or open a new node for the fix.** **M3.**                                                                                                                                  | A list with no actions accumulates and gets ignored; automatic re-running would let one decision change silently restart thirty nodes.                                                                                                                                    |
| D38 | Returning to the board                                    | **A digest of what changed since you last looked.** Its delta half comes from a fetch and two git refs; its snapshot half — results waiting, nodes flagged — needs neither. **M3.**                                           | A filter over data that already exists, with nothing stored. With no remote the snapshot half still works, which is the half a single user needs.                                                                                                                         |
| D39 | A run that fails                                          | **The node returns to `ready` with a "last run failed" flag**, its error, log, branch and worktree kept.                                                                                                                      | A flag, not an eighth status. The flag is local, and it stops a queued chain.                                                                                                                                                                                             |
| D40 | Worktree lifecycle                                        | **One per node.** Removed automatically after accept; preserved after reject, stop, or failure. A cleanup command lists idle worktrees with their size and asks before removing them.                                         | If the work landed, the worktree is done. Per node rather than per run means dependencies install once (ADR 0012).                                                                                                                                                        |
| D41 | Removing nodes and decisions                              | **Archive is the normal path**; permanent deletion is refused while anything still references the record, and the referencing nodes are named.                                                                                | Archiving keeps the history and is reversible. The same refusal runs again after a board merge, where the reference can arrive from someone else.                                                                                                                         |
| D42 | Schema version across teammates                           | **`project.json` carries the schema version.** An older SOBER refuses to open a newer board; a newer SOBER migrates an older one. **M2.**                                                                                     | Refusing to read is the only safe direction: a version that does not understand a field drops it on write.                                                                                                                                                                |
| D6  | Where the build manifesto lives                           | **`docs/MANIFESTO.md`**, stating explicitly that it shapes which capabilities become MUST but does not override SCOPE's rule 1.                                                                                               | A preference for user experience over build cost is an argument for putting something in MUST, never a licence to build something that is not in MUST.                                                                                                                    |

## 5. Running agents

| ID       | Requirement                                                                                                                                                                                                                                                                                        | MUST  |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| PR-05-01 | The Run action is available only on a node that is ready with an approved brief. Otherwise it is disabled and says why.                                                                                                                                                                            | 3, 4  |
| PR-05-02 | Every node has one git worktree on one branch, for its whole life. Attempts add commits. No run ever touches the user's checkout or the main branch.                                                                                                                                               | 4, 5  |
| PR-05-03 | The agent runs in the user's own host tool, headless. SOBER never asks for an API key and never chooses the model.                                                                                                                                                                                 | 4     |
| PR-05-04 | Before starting, SOBER checks the host tool is installed and authenticated, and that the worktree's setup command succeeds. ## 9. Rules and limits

Always in force, not tied to a step. These become CI thresholds and lint rules in
phase 0, before any product code exists.

| ID       | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                             | MUST     |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| PR-09-01 | The dashboard stays interactive with 200 active nodes on the canvas, and does not fall over at 1,000: panning, dragging, hover, and opening the detail panel do not stall.                                                                                                                                                                                                                                                              | 6        |
| PR-09-02 | SOBER's own overhead on a dispatch is negligible against the agent session it wraps. Running a node through SOBER is not slower than running the same session by hand.                                                                                                                                                                                                                                                                  | 4        |
| PR-09-03 | The surfaces a human reads and writes are the host session and the dashboard. Everything else — the board branch, local state, the internal formats — is machine-facing, and no workflow requires a human to open them.                                                                                                                                                                                                                 | 6, 7, 12 |
| PR-09-04 | Windows, macOS, and Linux are all first-class. Native on each, with no shell, container, or WSL requirement. No POSIX-only primitive reaches the code; this is a lint rule, not a convention.                                                                                                                                                                                                                                           | 7, 8     |
| PR-09-05 | An agent cannot land its own work: it cannot merge its branch, and it cannot mark its own result accepted. Only a human can.                                                                                                                                                                                                                                                                                                            | 5        |
| PR-09-06 | Every dispatch result passes an automatic security scan before it is shown for review: leaked secrets, plus a documented list of signals. A finding is surfaced, never silently dropped — and neither is a scan that could not run. A project may add rules for its own secret formats and suppress a known false positive; the review names which rule set ran, so what the scan does not cover stays documented next to what it does. | 5        |
| PR-09-07 | `.sober/` never holds a secret, and `.sober/local/` is gitignored. Nothing under `.sober/` that reaches git carries credentials.                                                                                                                                                                                                                                                                                                        | 8        |
| PR-09-08 | The dashboard is the primary surface for the board; the CLI and the MCP server can nevertheless perform every **state-changing** operation the dashboard can, headless. The CLI is the contract test, not the lesser twin.                                                                                                                                                                                                              | 6, 7, 12 |
| PR-09-09 | Behaviour that depends on real git state or a real subprocess — sync, conflicts, worktrees, dispatch, the pull request path, and installing the published package — is covered by tests that run against a real repository, on all three platforms.                                                                                                                                                                                     | 7, 8     |
| PR-09-10 | Configuration that governs a run or a review — the setup command, the scan's rules and suppressions — is read from the base ref, never from the branch under review (ADR 0019).
