## 3. SWE

### KRİTİK — v0'ın düştüğü, v1'in adlandırmadığı üç boşluk

**3.1 Atomik yazma yok.** DESIGN.md'de `rename`, `fsync`, "atomic" kelimeleri
geçmiyor. §8.4 bozuk dosyayı *okurken* tolere ediyor, *yazarken* önlemiyor. v0
`storage.ts:104-136` çıplak `writeFileSync` idi.
Senaryo: dispatch sırasında proses ölür → `nodes/<id>.json` yarım, node "broken record".
**Fix:** `core`'da tek `writeRecord()`: temp + `fsync` + `rename`. Tüm yazıcılar
buradan geçer. Yarım gün. ADR gerekmez, DESIGN §1.1'e üç satır.

**3.2 Aynı makinede eşzamanlı yazıcı kilidi yok.** `DESIGN.md:71-72` optimistic
concurrency'yi sadece board-branch sync (M2) için tanımlıyor. M1'de bile CLI + MCP
(host session) + phase 5'te server aynı `.sober/`'a aynı anda yazar. v0 bunu
çözmüştü (`storage.ts:336-370`, O_EXCL + PID-liveness lock); v1 miras almıyor.
Senaryo: dashboard'da accept, aynı anda `sober run` → lost update.
**Fix:** Dosya kilidi, stale kilit için heartbeat timestamp (PID sinyali değil —
Windows). ADR 0025. Not: v0'ın `process.kill(pid, 0)` yaklaşımı POSIX-only, taşıma.

**3.3 Dispatch timeout ve zorla sonlandırma yok.** ADR 0009:15 timeout'u reddedilen
tasarımın sorunu olarak sayıyor; yerine gelen adapter tasarımı da çözmüyor. Maliyet
kontrolü sadece concurrency=3. D31 "stop" ürün davranışı var, process-kill
mekanizması yazılmamış; MCP'den tetiklenen dispatch'in iptal yolu yok.
Senaryo: `claude -p` takılır → worktree, kilit (3.2 ile) ve fatura süresiz açık.
**Fix:** `dispatch.timeoutMinutes` config alanı + zorunlu `kill()`; `sober stop`
her yüzeyden erişilebilir. DESIGN §5.4'e bir paragraf.

### YÜKSEK

**3.4 Worktree kaldırırken dirty-check yok.** DESIGN.md'de `dirty`, `uncommitted`,
`porcelain` geçmiyor. v0 `dispatch.ts:117-120` `worktree remove --force` → `rmSync`
fallback ile commit'lenmemiş dosyaları sessizce siliyordu.
**Fix:** kaldırmadan önce `git status --porcelain`; kirliyse reddet ve söyle.

**3.5 Windows CI'da test ediliyor, tasarımda yok.** `DESIGN.md:1120-1128` sadece
"CI yakalar" diyor. 3.2'deki kilit tasarımı baştan platform-agnostik olmalı.

**3.6 `core` export sınırı yok.** Snapshot testi (`BUILD-PLAN.md:210-221`) büyümeyi
görünür kılar, durdurmaz. Tek reviewer yorulunca yine 291'e gider.
**Fix:** snapshot + yumuşak tavan (>60 export → CI warning). Tek satır.

### ORTA

**3.7 Coverage ratchet'in aracı yok.** ADR 0014:57 "never lower than last commit"
diyor; bunu yapan hazır Vitest özelliği yok. ~30 satır script: `coverage-summary.json`
commit'le, CI'da öncekiyle karşılaştır. Phase 0'a yazılmalı.

**3.8 Schema version M1'de sessiz.** Migration M2 doğru; ama M1 boyunca şema 5 fazda
değişecek. `schemaVersion` alanı var (ADR 0021:68-76) — M1'de sadece "eşleşmiyorsa
net hata ver, dur" eklenmeli. Birkaç satır.

**3.9 `core` içi git modül sınırı tanımsız.** v0'da git mantığı 9 dosyaya dağılmıştı.
Phase 2 planına `core/src/git/{worktree,merge,branch}.ts` olarak yazılsın.

**3.10 Tek reviewer + 2-agent cap + elicitation-only karar.** Darboğaz ama kasıtlı,
belgelenmiş, MCP-elicitation-yok fallback'i var (`DESIGN.md:292-294`). Aksiyon yok.

## 4. UX

### 4.1 Zaman modeli

6 node, 2 decision (1 paylaşılan), concurrency 3, node başına ~8 dk ajan, ~100
satır diff.

| Adım | M1 insan-aktif | M3 insan-aktif | Vibe-coding |
|---|---|---|---|
| Frame | 2 dk | 2 dk | 2 dk |
| Decompose + batch accept | 2 | 2 | — |
| Decide ×2 (elicitation) | 7 | 7 | ~0 (prompt içinde örtük) |
| Brief onay ×6 | 10 | 12 | — |
| Dispatch | 0.5 | 0.5 | seri, 10–12 dk duvar |
| Review ×6 | 18 | 15 | 8–10 |
| Accept ×6 | 1.5 | 1 | 1 |
| **Toplam insan-aktif** | **~41** | **~40** | **~22–25** |
| Duvar saati | ~57 | ~56 | ~25 |
| Context switch | 3–4 | ~2 | 0 |

Planlama (decompose+decide+brief) **~19–24 dk** — vibe-coding'in tüm döngüsüne
eşit. ADR 0017 bunu kendisi kabul ediyor (12–22 dk vs 2–5 dk). M3, M1'den hızlı
değil; kazancı görünürlük (digest, canvas).

### 4.2 Blokajlar

| Blokaj | Batch? | Default? | Charter'a dokunmadan esnetilebilir mi |
|---|---|---|---|
| Decomposition accept | Evet, zaten var | — | Zaten esnek |
| Decision (elicitation) | Hayır, tasarım gereği | `suggested` var | Hayır — "human picks" |
| Brief onayı | Hayır | approve-and-queue | Kısmen esnetilmiş |
| Dispatch onayı | approve-and-queue | Opt-in, asla default | Bilinçli |
| Review | Hayır | Hayır | Hayır — MUST #5 |
| Accept | Hayır (15 sn/node) | — | — |

Charter'ı bozmadan esnetilebilecek her yer zaten esnetilmiş.

### 4.3 Approve-and-queue kazandırıyor mu

Kısmen. Kazandırdığı: board'a dönüş sayısı (4–6 → 2–3) ve ajan duvar-saati.
Kazandırmadığı: insan-aktif süre, çünkü **review seri** ve tasarım bunu sadece
adlandırıyor (`BUILD-PLAN.md:139`), çözmüyor.

Masada kalan paralellik:
- Review'de toplu aksiyon yok. "Scan temiz + CI yeşil olan 4 node'u tek onayla kabul et" tasarımda yer almıyor. Digest (§7.1, M3) triyaj sağlıyor, okuma tek tek.
- Concurrency 3 ile 6 node = 2 dalga; review kuyruğu birikip aynı anda geliyor.
- Sonraki dalgada yeni decision çıkarsa zincir yine session'a dönüşü zorunlu kılar.

**KARAR VERİLDİ → ADR 0022.** Review = onaylanmış acceptance kriterlerine karşı
check sonuçları; diff isteğe bağlı. Yeşil node'lar (verify + scan + CI temiz) toplu
kabul: M1'de `sober accept --green`, M3'te review ekranı. `acceptance` bölümü ve
`dispatch.verify` M1'e girdi.

### 4.4 Doğrulanmamış UX varsayımları

1. **`sober review <node>` 200 satırlık diff için.** `DESIGN.md §6.2` sadece "findings diff'in üstünde" diyor; pager, highlight, dosya atlama, finding↔satır bağı yok. M2'ye (draft PR) kadar tek review yüzeyi ham terminal metni. M1 kullanıcısı en zayıf review deneyimini yaşıyor; emsaller (Codex, Copilot agent, Cursor) review'i GitHub PR arayüzüne devrediyor.
   **Fix (küçük):** M1'de `sober review` `--web` ile `gh pr view --web`'e düşsün, ya da diff'i `$PAGER`/`delta`'ya versin. Bir satır config.
2. **Elicitation'ın kart formatı.** Claude Code elicitation JSON-schema'dan generic form üretiyor (enum → dropdown, string → text). ADR 0010'un "seçenek + reason + costLater" kartı bu widget'lara sığmıyor; reason/costLater `description`'a sıkışacak. **Phase 3'te ilk gün bir spike:** 3 seçenekli gerçek bir elicitation aç, nasıl göründüğüne bak. Tasarım dokümanı ile render arasındaki fark ölçülmeden brief/decision UX'i yazılmamalı.

### 4.5 Emsal

Hiçbir emsal (Claude plan mode, Cursor background agents, Codex cloud, Copilot
agent, Devin, vibe-kanban) kalıcı, paylaşılan, gerekçeli decision kaydı tutmuyor.
SOBER'ın gerçek farkı bu. Zayıf yanı: M1 review deneyimi ve planlama yükü.

**Hüküm:** "SOBER vibe-coding'den yavaş olmamalı" hedefi, charter'ın kendi
cümlesiyle çelişiyor (`CHARTER.md:30` "Speed is a side effect, never the goal").
İkisinden biri seçilmeli:

**KARAR VERİLDİ → ADR 0022.** İnsan kodu okumaz; çıktıyı sıkı kriter ve testlerle
zorlar. Zaman modeli yeniden: review ~18 dk → ~4 dk, toplam ~41 → ~27 dk; vibe-coding
~22. Kalan ~5 dk fark = decision'lar = eğitim sütununun bedeli. Charter'ın "hız yan
etkidir" cümlesi kalır; hedef artık ölçülebilir.
