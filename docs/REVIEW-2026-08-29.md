Weighed across five areas: industry standards, structure, SWE, future (→ `PLAYBOOK.md`), UX. Every finding was measured or verified in the docs with `file:line`. The v0 numbers were re-measured on `~/Developer/sober-v0` with `git ls-files` + `wc -l`.

Items that need a ruling are marked **[DECISION]**. No ruling was given for them; the options are ranked, the recommended one first.

## 3. SWE

### CRITICAL — three gaps v0 fell into and v1 does not name

**3.1 No atomic write.** The words `rename`, `fsync`, "atomic" do not appear in DESIGN.md. §8.4 tolerates a broken file when _reading_, it does not prevent one when _writing_. v0 `storage.ts:104-136` was a bare `writeFileSync`. Scenario: the process dies during dispatch → `nodes/<id>.json` half-written, node is a "broken record". **Fix:** one `writeRecord()` in `core`: temp + `fsync` + `rename`. All writers go through it. Half a day. No ADR needed, three lines in DESIGN §1.1.

**3.2 No lock for concurrent writers on the same machine.** `DESIGN.md:71-72` defines optimistic concurrency only for board-branch sync (M2). Even in M1, CLI + MCP (host session) + the server in phase 5 write to the same `.sober/` at the same time. v0 had solved this (`storage.ts:336-370`, O_EXCL + PID-liveness lock); v1 does not inherit it. Scenario: accept in the dashboard, `sober run` at the same moment → lost update. **Fix:** a file lock, with a heartbeat timestamp for stale locks (not a PID signal — Windows). ADR 0025. Note: v0's `process.kill(pid, 0)` approach is POSIX-only, do not carry it over.

**3.3 No dispatch timeout and no forced termination.** ADR 0009:15 lists timeout as a problem of the rejected design; the adapter design that replaced it does not solve it either. Cost control is only concurrency=3. D31 "stop" exists as product behavior, the process-kill mechanism is not written; a dispatch triggered from MCP has no cancel path. Scenario: `claude -p` hangs → the worktree, the lock (with 3.2), and the bill stay open indefinitely. **Fix:** a `dispatch.timeoutMinutes` config field + a mandatory `kill()`; `sober stop` reachable from every surface. One paragraph in DESIGN §5.4.

### HIGH

**3.4 No dirty check when removing a worktree.** `dirty`, `uncommitted`, `porcelain` do not appear in DESIGN.md. v0 `dispatch.ts:117-120` silently deleted uncommitted files with `worktree remove --force` → `rmSync` fallback. **Fix:** `git status --porcelain` before removing; if dirty, refuse and say so.

**3.5 Windows is tested in CI, absent from the design.** `DESIGN.md:1120-1128` only says "CI catches it". The lock design in 3.2 must be platform-agnostic from the start.

**3.6 No `core` export limit.** The snapshot test (`BUILD-PLAN.md:210-221`) makes growth visible, it does not stop it. When the single reviewer tires it goes back to 291. **Fix:** snapshot + soft ceiling (>60 exports → CI warning). One line.

### MEDIUM

**3.7 The coverage ratchet has no tool.** ADR 0014:57 says "never lower than last commit"; no ready Vitest feature does that. A ~30-line script: commit `coverage-summary.json`, compare with the previous one in CI. Should be written into phase 0.

**3.8 Schema version is silent in M1.** Migration in M2 is right; but the schema will change across 5 phases during M1. The `schemaVersion` field exists (ADR 0021:68-76) — M1 only needs "if it does not match, give a clear error and stop". A few lines.

**3.9 The git module boundary inside `core` is undefined.** In v0 git logic was spread over 9 files. Write it into the phase 2 plan as `core/src/git/{worktree,merge,branch}.ts`.

**3.10 Single reviewer + 2-agent cap + elicitation-only decisions.** A bottleneck, but deliberate, documented, with a no-MCP-elicitation fallback (`DESIGN.md:292-294`). No action.

## 4. UX

### 4.1 Time model

6 nodes, 2 decisions (1 shared), concurrency 3, ~8 min of agent time per node, ~100-line diff.

| Step | M1 human-active | M3 human-active | Vibe-coding |
| --- | --- | --- | --- |
| Frame | 2 min | 2 min | 2 min |
| Decompose + batch accept | 2 | 2 | — |
| Decide ×2 (elicitation) | 7 | 7 | ~0 (implicit in the prompt) |
| Brief approval ×6 | 10 | 12 | — |
| Dispatch | 0.5 | 0.5 | serial, 10–12 min wall |
| Review ×6 | 18 | 15 | 8–10 |
| Accept ×6 | 1.5 | 1 | 1 |
| **Total human-active** | **~41** | **~40** | **~22–25** |
| Wall clock | ~57 | ~56 | ~25 |
| Context switches | 3–4 | ~2 | 0 |

Planning (decompose+decide+brief) is **~19–24 min** — equal to vibe-coding's whole loop. ADR 0017 admits this itself (12–22 min vs 2–5 min). M3 is not faster than M1; its gain is visibility (digest, canvas).

### 4.2 Blockers

| Blocker | Batch? | Default? | Can it be loosened without touching the charter |
| --- | --- | --- | --- |
| Decomposition accept | Yes, already exists | — | Already loose |
| Decision (elicitation) | No, by design | `suggested` exists | No — "human picks" |
| Brief approval | No | approve-and-queue | Partly loosened |
| Dispatch approval | approve-and-queue | Opt-in, never default | Deliberate |
| Review | No | No | No — MUST #5 |
| Accept | No (15 s/node) | — | — |

Every place that can be loosened without breaking the charter is already loosened.

### 4.3 Does approve-and-queue pay off

Partly. What it saves: the number of returns to the board (4–6 → 2–3) and agent wall-clock time. What it does not save: human-active time, because **review is serial** and the design only names this (`BUILD-PLAN.md:139`), it does not solve it.

Parallelism left on the table:

- Review has no batch action. "Accept the 4 nodes with a clean scan + green CI in one approval" is not in the design. The digest (§7.1, M3) gives triage, reading is one by one.
- With concurrency 3, 6 nodes = 2 waves; the review queue piles up and arrives all at once.
- If a new decision appears in the next wave, the chain again forces a return to the session.

**[DECISION] made → ADR 0022.** Review = check results against the approved acceptance criteria; the diff is optional. Green nodes (verify + scan + CI clean) are accepted in batch: `sober accept --green` in M1, the review screen in M3. The `acceptance` section and `dispatch.verify` entered M1.

### 4.4 Unverified UX assumptions

1. **`sober review <node>` for a 200-line diff.** `DESIGN.md §6.2` only says "findings above the diff"; no pager, highlight, file skipping, finding↔line link. Until M2 (draft PR) the only review surface is raw terminal text. The M1 user gets the weakest review experience; precedents (Codex, Copilot agent, Cursor) hand review off to the GitHub PR interface. **Fix (small):** in M1, `sober review` falls through to `gh pr view --web` with `--web`, or hands the diff to `$PAGER`/`delta`. One line of config.
2. **The elicitation card format.** Claude Code elicitation builds a generic form from JSON schema (enum → dropdown, string → text). ADR 0010's "option + reason + costLater" card does not fit these widgets; reason/costLater will get squeezed into `description`. **A spike on day one of phase 3:** open a real elicitation with 3 options and look at how it renders. Brief/decision UX should not be written before the gap between the design doc and the render is measured.

### 4.5 Precedent

No precedent (Claude plan mode, Cursor background agents, Codex cloud, Copilot agent, Devin, vibe-kanban) keeps a persistent, shared, reasoned decision record. That is SOBER's real difference. Its weak side: the M1 review experience and the planning load.

**Ruling:** The goal "SOBER must not be slower than vibe-coding" contradicts the charter's own sentence (`CHARTER.md:30` "Speed is a side effect, never the goal"). One of the two must be chosen:

**[DECISION] made → ADR 0022.** The human does not read code; they force the output through strict criteria and tests. Time model again: review ~18 min → ~4 min, total ~41 → ~27 min; vibe-coding ~22. The remaining ~5 min gap = decisions = the price of the education pillar. The charter's "speed is a side effect" sentence stays; the goal is now measurable.
