# SOBER v1 — plan review, 2026-08-28

An audit of `CHARTER.md`, `SCOPE.md`, `PRODUCT.md`, `DESIGN.md`, `STRUCTURE.md`,
`MANIFESTO.md` and `adr/0001–0005`, against v0 as it actually stands on disk.

Nothing here is a scope change. Every item is either a contradiction between two
documents, a MUST with no mechanism behind it, or a mechanism with a hole in it.
Fixes are proposed; none is accepted until an ADR says so.

## Blockers — decide before any phase 1 code

### B1. A referenced-but-not-introduced decision does not hold anything

`DESIGN.md` §2.2: "A node is held **if and only if** a decision it _introduces_
is still open. A node that only references a decision is not held by it; it waits
on the introducing node like any other dependency."

The second sentence is a claim, not a mechanism. Nothing creates that dependency.
Take the example in §2.2 and §3.1: node `payments` has
`decisions: ["auth-model"]`, `introduces: []`, and no `dependsOn` path to
`auth-api`. Then, by §3.2:

- rank 4 `blocked` — no unfinished dependency, so no
- rank 5 `held` — nothing in `introduces`, so no
- rank 7 → **`ready`**

The node is dispatchable, and §3.7 renders its brief with `chosen: null` for an
unanswered decision. The one hard block is bypassed by omitting one array entry —
and §2.2 itself says `introduces` is "usually empty".

**Fix (one line):** a node is `held` if **any** decision in `decisions` is open.
`introduces` stops being the gate and keeps its real job: naming where the
decision is answered and who owns the answer.

This does not revive v0's failure. v0 blocked 22 of 56 nodes because every node
carried its **own copy** of every category — repetition. Here the record is
shared, so one answer clears every referencing node in the same write. The gate
gets _simpler_, not heavier.

Alternative, if `introduces` must stay the gate: `core` refuses to save a node
that references a decision without a `dependsOn` path to its introducer. That is
a validation rule, a cycle-adjacent graph walk, and a class of confusing error
messages — for the same outcome.

### B2. `cli` is published, `core` is never published

`STRUCTURE.md` → Publishing: `cli` **yes**, `core` **never**. `cli` depends on
`core` as `workspace:*`. On publish, `workspace:*` resolves to a real version
range — of a package that does not exist on the registry. `npm i -g @besober/cli`
then fails at install, which is `PR-00-01`'s entire subject.

Appendix A's own note — "`workspace:*` resolves at publish time" — is the
sentence that hides the problem: it can only resolve to something published.

**Fix:** decide the packaging story in phase 0, not phase 3. Bundle `cli` (tsup /
unbuild, workspace deps inlined, `core` never leaves the repo) and add
`publint` + `@arethetypeswrong/cli` as required checks on the published package.
Both are npm packages with no install script; both catch exactly the class of bug
that otherwise surfaces first in a user's terminal.

The same question applies to the dashboard's built assets: the CLI serves them,
so they must be inside the CLI tarball. v0 solved this with
`prepack: build:client` and `files: ["dist"]`. `STRUCTURE.md` does not mention it.

### B3. The dashboard cannot import `core`

`STRUCTURE.md`'s layout is `apps/dashboard # React + Vite`, and phase 4's gate is
"consumes `core` only". `core` owns `fs`, `git`, and the local database. A browser
bundle cannot import it. So an HTTP boundary exists — and it appears in no
layout, no phase, and no dependency-cruiser rule.

This is where phase 4 breaks, and phase 4 was 76% of v0.

**Fix:** name it now. Either `apps/dashboard` is the Vite client and the server
lives in the CLI, or the server is its own package. Then put the wire types in
`schema` so client and server cannot drift untyped, and add the
dependency-cruiser rule that forbids the client from importing `core` at all.
"Dashboard consumes `core` only" as written cannot be enforced, because it cannot
be true.

### B4. Three MUSTs depend on an agent call that is not designed

D28 and §5.1 describe how a **dispatch** launches a host CLI. But decomposition
(MUST #10), decision options (MUST #2) and the brief's written section (MUST #3)
are also agent calls, made from the dashboard, with a human waiting.

Nothing states: who invokes them, what prompt shape, what happens on a non-zero
exit, whether output is streamed, whether the call is cancellable, whether it
consumes a host session the user is billed for, or what the surface shows for the
30–90 seconds it runs. `DESIGN.md` §2.6's "the surface says that options are
being produced" is the only sentence on the subject.

This is the largest undesigned area in the plan, and it sits under the three
capabilities that make SOBER feel different from a task board.

**Fix:** one ADR — "the advisory channel" — covering invocation, failure,
cancellation and cost, consumed by phase 2. Plus a requirement in section 9: an
advisory call never blocks the surface, always shows progress, and is always
cancellable. `PR-09-02` only budgets dispatch overhead; it says nothing about the
latency the human actually sits through.

### B5. MUST #9 has no tool and no phase

ADR 0002 moves the security scan into MUST, then says "phase 3 (`cli`) **or**
phase 4 (`dashboard`) cannot ship review without the scan". "Or" is not an owner.
`STRUCTURE.md`'s build order does not mention the scan at all, and no document
names a scanner.

A MUST with no phase becomes a SHOULD by attrition. That is how v0's Auditor
ended up an MVP.

**Fix:** assign it to phase 3 and name the tool. `secretlint` is the pick that
fits `PR-00-01`: an npm package, no binary to fetch, no separate runtime. Secrets
are the half a machine reliably catches; "injection-shaped changes" is the vaguer
half, and it should be written as a short, stated list of patterns rather than a
promise. What the scan does **not** catch belongs in the docs next to what it
does.

## What is right, and worth defending under pressure

Not padding — these are the parts that should survive every later argument.

1. **Derived status.** A stored status is a field someone forgets. Seven derived
   statuses with a stated precedence order is better than most shipped task
   tools, and the reasoning for `blocked` > `held` (§3.2) is correct and
   non-obvious: option quality depends on upstream answers existing.
2. **One record per entity, one file per record.** The right call for git merge
   granularity, and Appendix A's rejection of a split across two branches names a
   failure mode most people discover in production.
3. **The brief is computed, not stored** (D24). This removes an entire class of
   staleness bug by construction, which is the strongest kind of fix.
4. **One hard block.** "One hard block is enforceable and five get routed around"
   is the single most valuable sentence in the documents.
5. **ADR 0001's selection criterion** — "which prose rule does this turn into a
   red CI check" — is the correct lesson from v0, correctly generalised.
6. **`accepted` as the record that makes a node done.** No `done` boolean to
   forget. Same class of fix as #3.
7. **Traceability.** Every requirement carries its MUST; every non-obvious choice
   carries a decision row. For a solo greenfield project this is above industry
   norm, and it is why this review could be written at all.

## UX: what planning actually costs

`MANIFESTO.md`'s own metric is "the share of users who say this is too
complicated". So the number that matters is human minutes before the first line
of code, and whether parallel dispatch pays them back.

Counted from the requirements as written, for a first project of 20 nodes and 8
decisions:

| Step                              | Human actions                                | Waiting                         | Estimate         |
| --------------------------------- | -------------------------------------------- | ------------------------------- | ---------------- |
| Intent                            | 1 free-text                                  | —                               | 2–5 min          |
| Decomposition                     | 1 batch accept over 20 proposals             | 1 agent call                    | 5–10 min         |
| Decisions                         | 8, **one at a time**, no batch (`PR-03-08`)  | 8 agent calls, on demand (D18)  | 16–32 min        |
| Briefs                            | 20, **one at a time**, no batch (`PR-04-05`) | 20 agent calls, on demand (D25) | 40–60 min        |
| Dispatch                          | 1 per node (`PR-01-09`), 3 at a time         | —                               | 5 min            |
| Review                            | 20 accept/reject                             | CI + scan pre-run               | 60–200 min       |
| **Before the first agent starts** |                                              |                                 | **≈ 65–110 min** |

Vibe coding reaches its first line of code in about five minutes. So yes: SOBER
is materially slower to start, and the documents never say for which project size
that trade is worth taking.

Three specific problems, all fixable without touching a MUST:

**U1 — brief approval is the largest cost and the least defensible.** Twenty
separate agent calls, each with the human sitting there waiting, because D25
generates on demand. D25's stated reason is "not for a node nobody intends to
run" — but a human who just dispatched a wave _does_ intend to run them. Batch
the **generation**, keep the **approval** per node. D26 is untouched; the waiting
disappears. Same for options: pre-generate for every open decision whose upstream
is finished, which satisfies D18's actual argument (options reasoned against
answers that exist) without generating thirty sets up front.

**U2 — nothing dispatches by itself.** `SCOPE.md` step 5 says "every ready node
runs as an isolated agent session, in parallel", but every requirement makes Run
a human click on a node. On a 20-node graph seven dependency levels deep, that is
seven return trips to the dashboard. This is the auto-dispatch that was supposed
to pay back the planning time, and it is not in the plan. It cannot be fully
automatic — brief approval is human by D26, and a brief cannot be rendered before
its upstream `outcome` exists (D27) — so the achievable version is **wave-based**:
when a wave of nodes becomes ready, generate all their briefs, then ask for the
approvals in one sitting, then dispatch the whole wave. One visit per wave
instead of one visit per node.

**U3 — the brief is too long to read twenty times.** `PR-04-02` shows the whole
rendered skeleton: project intent, every bound decision, files, upstream
outcomes. Approving twenty of those is how a per-node approval becomes a rubber
stamp through fatigue — the exact failure D26 exists to prevent, arriving through
a different door. Lead with the agent-written approach, which is the only part
that is new and the only part approval is really about; collapse the rest.

Two smaller ones:

- **Keyboard shortcuts.** The daily loop is decide → approve → review. Shortcuts
  for accept, approve and reject turn 90 minutes into 45. One requirement,
  section 9.
- **State the floor.** Below roughly five nodes, planning cannot pay for itself
  and SOBER should say so in its own docs. v0 had `.sober/quick/` for exactly
  this and v1 dropped it; manual node creation (`PR-02-06`) is now the only light
  path. Naming the floor is better than half-building a second one.

**Verdict.** As written, SOBER is slower than vibe coding and the payback
mechanism is missing. With wave briefing, wave approval and keyboard shortcuts,
pre-dispatch overhead drops to roughly 30–40 minutes and the parallel gain
becomes visible on the first project. None of the three costs a MUST.

Ranked, in the order the phases need them:

1. **B1** — before the schema exists. It changes one field's meaning.
2. **B2, B3, M7** — phase 0. They are packaging and boundary decisions and they
   are cheapest before any code.
3. **H8 + `BUILD-PLAN.md`** — before phase 1. Which requirements are in the
   walking skeleton.

5. **H1–H7, M1–M12, U1–U3** — into `DESIGN.md` and `PRODUCT.md` as the phases
